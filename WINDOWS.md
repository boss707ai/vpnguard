# VPN Guard для Windows — бриф на адаптацию

Готовой версии для Windows нет. Здесь задание для того, кто будет её делать, руками или с нейронкой. Mac-версия в этом репозитории — образец логики, тестов и подводных камней. Переносится принцип, а не код.

> **Важно:** всё про Windows ниже — варианты и гипотезы. На Windows это не проверялось. Первый шаг — проверка гипотезы на живой машине с автооткатом, код — только после неё. И ещё одно: ошибка в фильтре сетевого трафика может положить не программу, а всю машину. Поэтому — только штатные механизмы системы и обкатка часами под нагрузкой.

## Цель и модель угроз

- Ни один запрос к зарубежным адресам не уходит в интернет мимо VPN: VPN упал, не поднялся после перезагрузки, его забыли включить.
- «Дурак» — это и сам пользователь (выключил защиту и забыл), и AI-агенты, которые работают от его имени. Снять защиту без прав администратора они не должны.
- Это страховка VPN, не замена.

## Требования (как на Mac)

1. **VPN включён** — всё работает как обычно, включая раздельный роутинг клиента: российские сайты, которые клиент пускает напрямую, открываются.
2. **VPN выключен или упал** — зарубежное закрыто, DNS закрыт. Локальная сеть работает.
3. **Адреса VPN-серверов не зашиваются руками.** Защита берёт их из настроек VPN-клиента сама и сообщает о каждом новом сервере (уведомление — защита от подлога: настройки клиента может поменять любая программа пользователя). Имена серверов — через публичный DNS по HTTPS, а не через настройки клиента.
4. Фоновый сторож возвращает правила, если их снесли. После перезагрузки защита всегда включена, до входа пользователя.
5. **Пауза:**
   - по умолчанию 15 минут с автовозвратом;
   - можно выбрать срок;
   - есть «выключить совсем» — до ручного включения или перезагрузки;
   - снятие защиты — только с правами администратора (UAC), включение — без.
6. Значок в трее с состоянием. Уведомления: «VPN выключен — интернет закрыт», «добавлен VPN-сервер…», «правила не загрузились — работает аварийный набор».
7. Полное удаление возвращает систему как было.

## Принцип: решать по адресу назначения

**Mac-версия решает только по адресу назначения.** Мимо туннеля можно только: к VPN-серверам из настроек клиента, к DNS клиента (порты 53, 443, 853), в российские сети (тот же список, что у клиента), в локалку и DHCP. Всё остальное — только через туннель. Неважно, кто шлёт пакет.

**Почему не «по программе».** Фильтр по владельцу трафика (программам пользователя — только туннель, ядру VPN-клиента — куда угодно) кажется проще, но у него две проблемы:
- на macOS проверка владельца в pf (`user`) — редкий механизм: pf ищет сокет прямо при обработке пакета, под своей блокировкой, и это может увести ядро во взаимоблокировку;
- дыра с локальным прокси: Karing держит прокси «напрямую» (порт 3065 на 127.0.0.1). Любая программа может отдать ему запрос, а наружу его отправит ядро клиента — то есть «доверенный» владелец. Защита по владельцу это пропускает.

**Что это значит для Windows.**
- На Windows фильтр по программе (`-Program`, `FWPM_CONDITION_ALE_APP_ID`) — это штатный, массово используемый механизм брандмауэра, а не редкость, как `user` в pf. Его можно рассматривать. Но дыру с локальным прокси «напрямую» он не закрывает — её надо закрыть отдельно (выключить такой прокси в клиенте или запретить к нему подключения), иначе это не защита.
- Вариант «по адресу назначения», как на Mac v2, на Windows тоже возможен и дыры с прокси не имеет.
- Выбор — после проверки на живой машине, с явным сравнением рисков.

## Варианты на Windows (выбрать после проверки)

**A. Встроенный kill switch самого VPN-клиента.**
- В WireGuard для Windows есть опция блокировки трафика мимо туннеля, когда туннель на весь трафик.
- В клиентах на sing-box (Karing и другие) у режима TUN есть `strict_route`, который добавляет правила брандмауэра. Проверьте, что именно он закрывает: у sing-box это в первую очередь утечки DNS.
- Минус: встроенный kill switch обычно не страхует случай «клиент выключен или не запущен».

**B. Windows Defender Firewall через PowerShell (модуль NetSecurity).** Рекомендуемый старт.
- **Исходящая политика по умолчанию — блок:** `Set-NetFirewallProfile -DefaultOutboundAction Block`. Получается fail-closed: что не разрешено, не проходит.
- **Разрешающие правила (вариант «по адресу», как на Mac v2):**
  - всё на интерфейсе туннеля (`-InterfaceAlias` адаптера VPN или wintun);
  - адреса VPN-серверов из настроек клиента (`-RemoteAddress`), обновлять при смене профиля;
  - DNS клиента — порты 53, 443, 853 к его адресам;
  - российские сети (`-RemoteAddress` списком; проверьте предел числа адресов в одном правиле — сетей около 13 тысяч, может понадобиться несколько правил);
  - локальные подсети и DHCP;
  - системные службы — по необходимости.
- **Отличие от pf:** в Windows Firewall блокирующее правило сильнее разрешающего независимо от порядка. Поэтому строить надо как «блок по умолчанию + разрешения», а не «разрешения + общий блок правилом».
- **Все правила — в одной группе** (`-Group "VPNGuard"`): включать, выключать и удалять одним действием.
- **Что проверить на живой машине:**
  - как закрыть DNS — системный резолвер Dnscache работает как NETWORK SERVICE;
  - IPv6;
  - смену сети, сон и пробуждение;
  - локальный прокси клиента «напрямую»: не уходит ли через него зарубежный трафик.

**C. Windows Filtering Platform напрямую** (своя служба на C# или C++).
- Фильтры по адресу, приложению, SID: `FWPM_CONDITION_IP_REMOTE_ADDRESS`, `FWPM_CONDITION_ALE_APP_ID`, `FWPM_CONDITION_ALE_USER_ID`.
- Постоянные фильтры (persistent) переживают перезагрузку.
- Мощнее, но сложнее, и ошибка здесь дороже. Берите, если B не справится.

## Сторож и управление

- **Сторож** — служба или задача Планировщика от SYSTEM. Раз в несколько секунд проверяет правила и политику и чинит расхождения. Если всё на месте, ничего не перезагружает.
- **Каждый вызов системы — с таймаутом.** Системная команда не ответила за 10 секунд — не ждать вечно, а уведомить: система, похоже, зависла, пора сохранить работу.
- **Запасные наборы правил.** Не загрузился полный набор — загрузить урезанный, но безопасный (туннель, локалка), и сообщить. Никогда — «без правил», и никогда — «всё открыто».
- **Адреса серверов** — из настроек VPN-клиента. Если служба от SYSTEM их прочитать не может (на Mac настройки другой программы охраняет система), их передаёт процесс пользователя — значок; служба проверяет, что файл передачи создал именно пользователь, и не доверяет его содержимому больше, чем нужно (только адреса, не больше 64 штук).
- **Состояние** («включено» / «пауза до …» / «выключено») хранится там, где писать может только администратор. «Включить» — без прав: это безопасное направление.
- **Пауза** снимает всё своё и возвращает систему ровно в исходное состояние, по таймеру защита включается обратно. После перезагрузки — всегда «включено».
- **Значок в трее** — например, PowerShell с WinForms `NotifyIcon` или маленькое приложение. Снятие защиты — через запрос UAC.
- **Файлы, которые исполняет SYSTEM, — только в защищённом месте:** Program Files или ProgramData с правами только для администраторов и SYSTEM. Не в профиле пользователя, иначе агент подменит код, который исполнит SYSTEM.
- **Обновление** — через установленную копию установщика, с показом diff перед применением. Не запускать «свежий скрипт из папки пользователя» с правами администратора.

## Подводные камни с Mac (наверняка повторятся)

1. **Свой трафик VPN-клиента.** Соединение с сервером, «прямые» сайты и DNS клиента должны проходить напрямую. Сначала выясните, куда именно ходит клиент и к каким DNS.
2. **Не сломать трафик внутри туннеля.** На Mac правила с состояниями резали ответы локального обработчика sing-box в туннеле, и весь TCP через VPN вставал. Проверяйте TCP через туннель сразу после включения правил.
3. **DNS — отдельный канал.** При выключенном VPN системный резолвер ходит к роутеру и провайдеру. Это надо закрыть.
4. **Локальный прокси клиента «напрямую»** — обход защиты по владельцу (см. выше).
5. **Прямые правила клиента по доменам (geosite).** Защита по адресу не знает имён: российский сайт на зарубежном хостинге клиент пошлёт напрямую, а защита не пустит. В клиенте прямые правила должны быть только по IP (geoip) — тот же список, что у защиты.
6. **Сначала проверка гипотезы на живой машине** с автоматическим откатом правил через минуту, потом код. Без отката легко остаться без сети.
7. **Ничего не зашивать руками:** ни IP серверов, ни имена физических адаптеров (USB-Ethernet, мобильный роутер).
8. **Тестировать в том же окружении, где код работает.** Служба от SYSTEM — не ваша консоль: другие пути, другие права, другие версии утилит. И установщик — тоже код: тестируйте его так, как его исполнит оболочка, а не кусками по отдельности, иначе ошибка в кавычках проявится только у пользователя.
9. **Обкатка часами под нагрузкой**, а не только функциональные проверки на минуты: редкие ошибки сетевого фильтра проявляются под нагрузкой — контейнеры, тысячи сокетов, часы работы.

## Приёмка (по образцу `tests/acceptance.sh`)

- **VPN включён:** IP через туннель; сайты работают, в том числе «прямые» российские; DNS работает.
- **Принудительный обход туннеля** (запрос с привязкой к физическому адаптеру) к зарубежному адресу — мгновенный отказ; к российскому — проходит.
- **Локальный прокси клиента «напрямую»** к зарубежному адресу — отказ.
- **VPN выключен:** сайты, ping, DNS — отказ. Потом VPN-клиент подключается снова при включённой защите.
- **Сторож:** удалить правило или выключить брандмауэр — через несколько секунд всё вернулось, есть запись в журнале.
- **Пауза:** система как без защиты, потом автовозврат. «Выключить совсем» держится. «Включить» работает без админа.
- **Перезагрузка:** защита включена.
- **Обкатка:** часы под нагрузкой (контейнеры, много соединений), сеть и сторож живы (по образцу `tests/soak.sh`).
- **Удаление:** система как до установки.

## Промт для нейронки

```
Ты — инженер по безопасности Windows. Нужно сделать «страховку VPN» для Windows по брифу
WINDOWS.md из этого репозитория; mac-версия рядом (README.md, pf/vpnguard.rules, daemon/vpnguardd,
lib/state.sh, tests/acceptance.sh, tests/soak.sh, precheck.sh) — образец логики, тестов и
подводных камней. Особенно прочитай раздел «Принцип: решать по адресу назначения».

Мой VPN-клиент: [НАЗВАНИЕ], режим: [TUN / системный прокси].

Порядок работы:
1. Выясни, как ходит наружу ядро моего VPN-клиента (к каким серверам и DNS, каким процессом),
   как называется адаптер туннеля и есть ли у клиента локальный прокси «напрямую».
   Дай команды, я их выполню и пришлю вывод.
2. Сравни для моей машины вариант «по адресу назначения» и «по программе»: что каждый закрывает,
   чем рискует, насколько штатный механизм Windows под ним. Предложи один.
3. Предложи проверку гипотезы на живой машине: временные правила + автоматический откат
   через 60 секунд (даже если скрипт упадёт). Проверить: обход туннеля к зарубежному адресу
   режется, трафик через туннель и трафик ядра клиента проходят, DNS при выключенном VPN закрыт,
   локальный прокси «напрямую» не выпускает за рубеж.
4. Только после успешной проверки — реализация по требованиям брифа: правила, сторож от
   SYSTEM с таймаутами на каждый вызов, запасной набор правил, пауза с автовозвратом, значок
   в трее, снятие только через UAC, полное удаление, приёмочный тест и обкатка под нагрузкой.

Ограничения: не выключай брандмауэр целиком; не зашивай IP серверов руками — бери из настроек
клиента; все правила — в одной группе; файлы, которые исполняет SYSTEM, — только в защищённом
месте; только штатные механизмы Windows; перед каждым шагом с правами администратора объясняй,
что он делает и как его откатить.
```
